** DONE voc has command line options for setting machine address size and alignment.  Figure out if poc needs them too.
 Target machine address size and alignment (default is that of the running compiler binary)
    -A44   32 bit addresses, 32 bit alignment (e.g. Unix/linux 32 bit on x86).
    -A48   32 bit addresses, 64 bit alignment (e.g. Windows 32 bit on x86, linux 32 bit on arm).
    -A88   64 bit addresses, 64 bit alignment (e.g. 64 bit platforms).
Read voc's own OPM.Mod (src/compiler/OPM.Mod, ~line 269): -A takes two digits, address size then struct alignment, in bytes, and defaults to "that of the running compiler binary" - it exists because voc generates portable C source and has no other way to know what ABI the *downstream* C compiler will apply once it processes that C: address size and struct alignment are independent axes there (e.g. -A48, 32-bit addresses with 64-bit alignment, is real - old 32-bit Windows x86 and 32-bit ARM Linux both round some fields to 8-byte boundaries despite a 4-byte pointer), so voc must be told explicitly rather than infer it. Confirmed poc needs no equivalent flag, for a reason specific to compiling straight to LLVM IR rather than through C: LLVMCodeGenerator.Mod already emits an explicit "target datalayout" string (dataLayoutW64/dataLayoutW32, chosen by ConstantEvaluator.wordSize, itself set from the -target triple via Poc.Mod's SetWordSizeFromTriple) that pins down address size *and* alignment together, verified against real clang/hardware (Phase 8 step 13: OpenBSD i386's own datalayout string is genuinely different from Linux's, not just narrower - already handled). Choosing the target triple already chooses both axes at once, unlike voc's C-generation path where the two are genuinely independent and nothing downstream is told the triple at all. The two-datalayout table is deliberately narrower than voc's three-way split (only the word-size axis, not a separate alignment one) because poc's own stated portability targets - Linux, NetBSD, OpenBSD, FreeBSD, all mainstream Unix x86/ARM ABIs - never hit voc's -A48 case (pointer size and alignment diverging is a Windows/32-bit-ARM-specific oddity, not a Unix one); AGENTS.md/PLAN.md already document the two-datalayout table as scoped to "only the two triples actually verified on real hardware," so a target that genuinely needs a third, different datalayout is a LLVMTypes.Mod/LLVMCodeGenerator.Mod table-widening question when a real one is added, not a new CLI flag. The VAX/VMS backend (Phase 13) needs no such flag either: VAX is a single, fixed 32-bit-address architecture with its own fully-specified VMS Calling Standard layout rules, not a user-selectable axis at all.
** DONE MAX(T)/MIN(T)/SIZE(T) constant folding (the MAX(LONGINT)-in-CONST gap from the Phase 7 self-check entry below).
Reframed before implementing (per discussion): MAX/MIN/SIZE are not really *calls* in the report's sense - their argument position holds a bare *type* name, not a value expression, so folding them needs no general "evaluate a call's argument, then apply the function" machinery, just one more ConstExpr leaf shape resolved against a fixed bound - a much smaller problem than folding a value-argument predeclared function (ORD/ABS/CHR/etc, deliberately still deferred, not currently blocking anything). SIZE(T) implemented too, folding via MemoryLayout.wordSize32/sizeModelO2 (poc's existing "-O2 default" precedent, since there's no real -O2/-OC CLI flag yet to pick a target from). Writing minShortInt/minInteger/minLongInt as bare negated literals (-128 etc.) turned out to be wrong: any two's-complement type's minimum magnitude is by construction one more than its own maximum, so poc's own minimal-type rule always folded the bare literal one rank wider - fixed by computing them as -maxX - 1 instead, the same technique minHugeInt already needed. ** DONE Phase 7 self-check milestone: poc -check on its own front-end source.
Pointing poc's own -check at its front-end modules (PLAN.md's Phase 7 milestone) surfaced three real, previously-undetected bugs, all fixed and regression-tested (86/86 conformance tests still pass): (1) SemanticActions.ResolveQualidentType used *resolution order* as a proxy for declaration order when deciding whether a record field's forward reference to another type is legal - wrong whenever a pointer's eager base-resolution runs ahead of the main pass, which is exactly what happens with SyntaxTree.Mod's own "declare every POINTER up front, give bodies later" idiom. (2) Diagnostics.Mod's Reset* did "fileName := name" (an open-array ARRAY OF CHAR parameter assigned to a fixed array) - voc accepts this as an extension, but Oberon2.pdf's own assignment-compatible rule 6 only covers a *string constant*, not a general array value, so this was a real, previously-undetected violation of poc's own strict-bootstrap-source constraint. Fixed with the report's own COPY predeclared procedure. (3) Oberon2.pdf §3's vocabulary rule 4 ("a string of length 1 can be used wherever a character constant is allowed and vice versa") was never implemented at all, silently blocking the ordinary single-quoted-character idiom used throughout Lexer.Mod (ch = ":", CASE ch OF "a": ...). (5) PredeclaredProcedures.Mod's own ORD check didn't recognize a length-1 string literal either (the same §3 vocabulary rule as (3), a separate call site) - fixed with a small, deliberately duplicated IsSingleCharStringLiteral (this module cannot import SemanticActions.Mod, per its own header comment's established precedent). SyntaxTree/Diagnostics/Lexer/Types/MemoryLayout/SymbolTable/ConstantEvaluator/PredeclaredProcedures now all self-check clean except for the one already-documented, separate MAX(LONGINT)-in-CONST gap (PLAN.md's "Open design questions"); ModuleInterface/SemanticActions/Parser/Poc.Mod remain blocked on Appendix C/SYSTEM.BYTE (also undocumented until now, not fixed - a separate, larger feature).

** DONE Resolve CONST/TYPE/VAR declarations as one linear pass in textual order, not three separate section-wide passes (the "Relax order of declarations" gap from the SIZE(Rec) entry above).
Confirmed directly against real voc first (2026-09-17, see PLAN.md's "Declaration order" entry): voc does *not* allow general forward references - only its two standard exceptions (a POINTER's own inline base type, PROCEDURE^ forward declarations) - it just resolves CONST/TYPE/VAR declarations in one linear textual-order pass, and separately allows CONST/TYPE/VAR *sections* to appear in any order/be repeated and interleaved arbitrarily (poc's own Parser.Mod already parsed that part correctly - ParseDeclSeq's LOOP already accepted CONST/TYPE/VAR keywords in any order/repetition - the gap was purely on the SemanticActions side, which discarded that interleaving by sorting everything into three separate constDecls/typeDecls/varDecls lists before CheckModuleBody resolved them as three separate whole-section passes). So this was *not* "relax order of declarations" in the sense of adding forward references - it was removing an artificial three-pass batching that forced every CONST to resolve before every TYPE regardless of source order. Implemented as SemanticActions.ResolveDeclSeq: a PredeclareTypeNames pre-pass (still registers every TYPE name up front, unchanged in spirit, so the POINTER-base exception keeps working regardless of order) followed by one merged pass in true textual order (a three-way merge over the three still-separately-typed lists, keyed on each node's own line/column), replacing the old ResolveConstDecls/ResolveTypeDecls/ResolveVarDecls. Surfaced and fixed two real correctness gaps along the way, not deferred: (1) a pre-existing bug (reachable even without this change, via a standalone repro) where SemanticActions.ResolveQualidentType's forward-reference check was gated behind obj.pendingTypeNode.line, which gets cleared the moment a type resolves - so once an earlier POINTER's own base eagerly resolved a later type as a side effect, the check could no longer even ask the question, silently accepting a genuine forward reference voc rejects; fixed with a new, never-cleared SymbolTable.ObjectDesc.declLine/declColumn, checked before (not after) the "already resolved" fast path - ConstantEvaluator.LookupBareTypeName (MAX/MIN/SIZE's own separate lookup) needed the identical fix, restricted to unqualified references only, since a qualified M.T type's declLine is a different file's own line number entirely; missing that qualifier guard on the SemanticActions side first broke semantic-reject-readonly-import-field (caught immediately by the conformance suite). (2) moving TYPE's CheckExportMark into the new pre-declare pass reported "-" mark errors out of order relative to CONST/VAR's own (caught by semantic-reject-readonly-mark); fixed by deferring it to each type's own turn in the merged pass instead. Three new conformance tests: semantic-decl-order-const-refs-later-section-type, semantic-decl-order-interleaved-sections, semantic-reject-decl-order-const-forward-type. All 94 conformance tests pass; the Phase 7 self-check sweep's 8 clean modules are unaffected.
