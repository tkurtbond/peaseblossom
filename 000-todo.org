** DONE MAX(T)/MIN(T)/SIZE(T) constant folding (the MAX(LONGINT)-in-CONST gap from the Phase 7 self-check entry below).
Reframed before implementing (per discussion): MAX/MIN/SIZE are not really *calls* in the report's sense - their argument position holds a bare *type* name, not a value expression, so folding them needs no general "evaluate a call's argument, then apply the function" machinery, just one more ConstExpr leaf shape resolved against a fixed bound - a much smaller problem than folding a value-argument predeclared function (ORD/ABS/CHR/etc, deliberately still deferred, not currently blocking anything). MAX(T)/MIN(T) implemented for SHORTINT/INTEGER/LONGINT/HUGEINT/SET/CHAR/BOOLEAN (REAL/LONGREAL deliberately left out - needs its own voc-verified IEEE 754 bound, tied to the separate float-formatting work). SIZE(T) implemented too, folding via MemoryLayout.wordSize32/sizeModelO2 (poc's existing "-O2 default" precedent, since there's no real -O2/-OC CLI flag yet to pick a target from). Writing minShortInt/minInteger/minLongInt as bare negated literals (-128 etc.) turned out to be wrong: any two's-complement type's minimum magnitude is by construction one more than its own maximum, so poc's own minimal-type rule always folded the bare literal one rank wider - fixed by computing them as -maxX - 1 instead, the same technique minHugeInt already needed. Testing also surfaced two separate, undocumented-until-now gaps, recorded in PLAN.md's "Open design questions" rather than fixed here: SIZE(T)/MAX(T)/MIN(T) only work for a predeclared or imported T, not one declared in the same module (see the SIZE(Rec) entry below); and ConstantEvaluator's arithmetic folding doesn't re-derive a computed constant's minimal type from its actual value (only a bare literal token gets that treatment), so "MAX(SHORTINT) + 1" wrongly stays SHORTINT-typed even though real voc rejects it. Three new conformance tests: semantic-const-max-min-size, semantic-reject-const-max-min-too-wide, semantic-reject-const-max-min-not-a-type.
** DONE Compare voc's handling of SIZE(Rec) where Rec is declared in the current module to poc's handling.
Confirmed directly (2026-09-17): voc accepts "TYPE Rec = RECORD x, y: LONGINT END; CONST RecSize = SIZE(Rec);" in one module with no complaint. poc rejects the same source ("SIZE requires a type name argument") - not a SIZE-specific bug, but the existing "Relax order of declarations" gap (below): SemanticActions.CheckModuleBody resolves CONST declarations before TYPE declarations unconditionally, regardless of their relative textual order, so Rec's own TYPE declaration (even though textually first) is not yet in scope when the CONST section referencing it is processed. ** DONE Qualified WITH narrowing (WITH M.v: T DO).
The second, separate gap from "Type guards in designators?" above (see PLAN.md's own entry) - turned out not to be a narrowing gap at all. Direct experiment against real voc found it rejects WITH M.v: T DO outright (err 245, "guarded pointer variable may be manipulated by non-local operations") - a real memory-safety concern (an imported module's own procedure could reassign M.v during the guarded body, invalidating the narrowed type), which Oberon2.pdf §9.11 is silent on either way. Testing every shape directly against voc showed this is one instance of a broader rule voc applies to every pointer-typed WITH guard: also rejects a VAR parameter of pointer type and a variable assigned by bare name inside some other PROCEDURE anywhere in the module (a static check, not real reachability), while accepting a local var or global never assigned inside any PROCEDURE. SemanticActions.Mod's CheckWithGuard now implements the same three rejections (deliberately the simpler, strictly more-conservative half of voc's own rule - see its header comment). Four new conformance tests: semantic-reject-with-qualified-guard, semantic-reject-with-var-param-guard, semantic-reject-with-global-reassigned, semantic-with-value-param-guard.

** DONE Integer literal minimal-type folding (the gap found during the HUGEINT Appendix A/C survey above).
Oberon2.pdf §5: "the type of an integer constant is the minimal type to which the constant value belongs." ** DONE Phase 7 self-check milestone: poc -check on its own front-end source.
Pointing poc's own -check at its front-end modules (PLAN.md's Phase 7 milestone) surfaced three real, previously-undetected bugs, all fixed and regression-tested (86/86 conformance tests still pass): (1) SemanticActions.ResolveQualidentType used *resolution order* as a proxy for declaration order when deciding whether a record field's forward reference to another type is legal - wrong whenever a pointer's eager base-resolution runs ahead of the main pass, which is exactly what happens with SyntaxTree.Mod's own "declare every POINTER up front, give bodies later" idiom. Fixed by comparing actual source line positions instead; verified against real voc's exact acceptance/rejection boundary across four targeted cases (a field forward-referencing a later RECORD, a later extension base, a later POINTER-typed name, and the accepted bunched-pointer idiom). (2) Diagnostics.Mod's Reset* did "fileName := name" (an open-array ARRAY OF CHAR parameter assigned to a fixed array) - voc accepts this as an extension, but Oberon2.pdf's own assignment-compatible rule 6 only covers a *string constant*, not a general array value, so this was a real, previously-undetected violation of poc's own strict-bootstrap-source constraint. Fixed with the report's own COPY predeclared procedure. (3) Oberon2.pdf §3's vocabulary rule 4 ("a string of length 1 can be used wherever a character constant is allowed and vice versa") was never implemented at all, silently blocking the ordinary single-quoted-character idiom used throughout Lexer.Mod (ch = ":", CASE ch OF "a": ...). Implemented via a new SemanticActions.IsSingleCharStringLiteral helper (relational operators) plus value-dependent extensions to CheckAssignmentCompatible (assignment/RETURN/value-parameter passing, now also poc's first support for fixed-size ARRAY OF CHAR value parameters taking a string constant, previously missed by CheckArguments) and CheckCaseLabelList (CASE labels). Continuing the sweep surfaced two more real bugs, both fixed: (4) a diamond import (e.g. C IMPORTs A and B, and B itself IMPORTs A - an entirely ordinary shape) produced two independent, incompatible Types.Type graphs for the same declared module, since ResolveImport re-read and re-CheckModuleBody'd a .sym file fresh on every import edge with no caching; fixed with a LoadedModule cache (module name -> finished SymbolTable.Scope) threaded by VAR through CheckModuleBody/ResolveImport, populated only once a module's own resolution has fully finished so the pre-existing cyclic-import check is unaffected; confirmed with a minimal 3-module repro against real voc. (5) PredeclaredProcedures.Mod's own ORD check didn't recognize a length-1 string literal either (the same §3 vocabulary rule as (3), a separate call site) - fixed with a small, deliberately duplicated IsSingleCharStringLiteral (this module cannot import SemanticActions.Mod, per its own header comment's established precedent). Chasing that fix's own self-check run surfaced a sixth bug: ResolveImport's "did this .sym file parse cleanly" check compared Diagnostics.errorCount (deliberately global/cumulative across a whole compilation) against a bare "> 0" instead of a before/after snapshot, so once *any* earlier import failed anywhere, every subsequent import's .sym file was wrongly flagged "malformed" for the rest of the compilation even when it parsed fine - fixed by snapshotting errorCount immediately before parseModule and comparing the delta. SyntaxTree/Diagnostics/Lexer/Types/MemoryLayout/SymbolTable/ConstantEvaluator/PredeclaredProcedures now all self-check clean except for the one already-documented, separate MAX(LONGINT)-in-CONST gap (PLAN.md's "Open design questions"); ModuleInterface/SemanticActions/Parser/Poc.Mod remain blocked on Appendix C/SYSTEM.BYTE (also undocumented until now, not fixed - a separate, larger feature).

** DONE Resolve CONST/TYPE/VAR declarations as one linear pass in textual order, not three separate section-wide passes (the "Relax order of declarations" gap from the SIZE(Rec) entry above).
Confirmed directly against real voc first (2026-09-17, see PLAN.md's "Declaration order" entry): voc does *not* allow general forward references - only its two standard exceptions (a POINTER's own inline base type, PROCEDURE^ forward declarations) - it just resolves CONST/TYPE/VAR declarations in one linear textual-order pass, and separately allows CONST/TYPE/VAR *sections* to appear in any order/be repeated and interleaved arbitrarily (poc's own Parser.Mod already parsed that part correctly - ParseDeclSeq's LOOP already accepted CONST/TYPE/VAR keywords in any order/repetition - the gap was purely on the SemanticActions side, which discarded that interleaving by sorting everything into three separate constDecls/typeDecls/varDecls lists before CheckModuleBody resolved them as three separate whole-section passes). So this was *not* "relax order of declarations" in the sense of adding forward references - it was removing an artificial three-pass batching that forced every CONST to resolve before every TYPE regardless of source order. Implemented as SemanticActions.ResolveDeclSeq: a PredeclareTypeNames pre-pass (still registers every TYPE name up front, unchanged in spirit, so the POINTER-base exception keeps working regardless of order) followed by one merged pass in true textual order (a three-way merge over the three still-separately-typed lists, keyed on each node's own line/column), replacing the old ResolveConstDecls/ResolveTypeDecls/ResolveVarDecls. Surfaced and fixed two real correctness gaps along the way, not deferred: (1) a pre-existing bug (reachable even without this change, via a standalone repro) where SemanticActions.ResolveQualidentType's forward-reference check was gated behind obj.pendingTypeNode.line, which gets cleared the moment a type resolves - so once an earlier POINTER's own base eagerly resolved a later type as a side effect, the check could no longer even ask the question, silently accepting a genuine forward reference voc rejects; fixed with a new, never-cleared SymbolTable.ObjectDesc.declLine/declColumn, checked before (not after) the "already resolved" fast path - ConstantEvaluator.LookupBareTypeName (MAX/MIN/SIZE's own separate lookup) needed the identical fix, restricted to unqualified references only, since a qualified M.T type's declLine is a different file's own line number entirely; missing that qualifier guard on the SemanticActions side first broke semantic-reject-readonly-import-field (caught immediately by the conformance suite). (2) moving TYPE's CheckExportMark into the new pre-declare pass reported "-" mark errors out of order relative to CONST/VAR's own (caught by semantic-reject-readonly-mark); fixed by deferring it to each type's own turn in the merged pass instead. Three new conformance tests: semantic-decl-order-const-refs-later-section-type, semantic-decl-order-interleaved-sections, semantic-reject-decl-order-const-forward-type. All 94 conformance tests pass; the Phase 7 self-check sweep's 8 clean modules are unaffected.
