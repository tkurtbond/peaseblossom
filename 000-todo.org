** DONE Qualified WITH narrowing (WITH M.v: T DO).
The second, separate gap from "Type guards in designators?" above (see PLAN.md's own entry) - turned out not to be a narrowing gap at all. Direct experiment against real voc found it rejects WITH M.v: T DO outright (err 245, "guarded pointer variable may be manipulated by non-local operations") - a real memory-safety concern (an imported module's own procedure could reassign M.v during the guarded body, invalidating the narrowed type), which Oberon2.pdf §9.11 is silent on either way. Testing every shape directly against voc showed this is one instance of a broader rule voc applies to every pointer-typed WITH guard: also rejects a VAR parameter of pointer type and a variable assigned by bare name inside some other PROCEDURE anywhere in the module (a static check, not real reachability), while accepting a local var or global never assigned inside any PROCEDURE. SemanticActions.Mod's CheckWithGuard now implements the same three rejections (deliberately the simpler, strictly more-conservative half of voc's own rule - see its header comment). Four new conformance tests: semantic-reject-with-qualified-guard, semantic-reject-with-var-param-guard, semantic-reject-with-global-reassigned, semantic-with-value-param-guard.
** DONE MemoryLayout.Mod -O2/-OC elementary-type-size model.
Added a second axis (sizeModelO2/sizeModelOC) alongside the existing target-word-size parameter, mirroring voc's own selectable SHORTINT/INTEGER/LONGINT/SET widths. HUGEINT/REAL/LONGREAL/BOOLEAN/CHAR unaffected; HUGEINT and LONGINT both end up 8 bytes under -OC but stay distinct types. poc itself has no -O2/-OC CLI flag yet, since -dump-layout (the only caller) has nothing else to govern until a backend exists; it now prints all four word-size x size-model combinations unconditionally instead.
** DONE Integer literal minimal-type folding (the gap found during the HUGEINT Appendix A/C survey above).
Oberon2.pdf §5: "the type of an integer constant is the minimal type to which the constant value belongs." ConstantEvaluator.ParseDecimalInteger/ParseHexInteger now detect overflow past HUGEINT's own max digit-by-digit (reported as a diagnostic, "integer literal too large for HUGEINT", rather than silently wrapping); a new ConstantEvaluator.IntegerLiteralType picks the narrowest of SHORTINT/INTEGER/LONGINT/HUGEINT the value fits (voc's -O2 default byte widths, since poc has no -O2/-OC flag of its own yet to pick a target model from) and is shared by both ConstantEvaluator.EvaluateLiteral (CONST folding) and SemanticActions.CheckLiteralExpr (general expression typing, e.g. a plain assignment's RHS), which previously duplicated a hardcoded Types.Integer independently of ConstantEvaluator. Verified against real voc (2026-09-17): its default -O2 sizes reject a too-wide literal ("incompatible assignment") at exactly the same boundaries, and its own overflow diagnostic ("number too large") confirms HUGEINT's max. Three new conformance tests: semantic-integer-literal-minimal-type, semantic-reject-integer-literal-too-wide, semantic-reject-integer-literal-overflow.
** DONE Phase 7 self-check milestone: poc -check on its own front-end source.
Pointing poc's own -check at its front-end modules (PLAN.md's Phase 7 milestone) surfaced three real, previously-undetected bugs, all fixed and regression-tested (86/86 conformance tests still pass): (1) SemanticActions.ResolveQualidentType used *resolution order* as a proxy for declaration order when deciding whether a record field's forward reference to another type is legal - wrong whenever a pointer's eager base-resolution runs ahead of the main pass, which is exactly what happens with SyntaxTree.Mod's own "declare every POINTER up front, give bodies later" idiom. Fixed by comparing actual source line positions instead; verified against real voc's exact acceptance/rejection boundary across four targeted cases (a field forward-referencing a later RECORD, a later extension base, a later POINTER-typed name, and the accepted bunched-pointer idiom). (2) Diagnostics.Mod's Reset* did "fileName := name" (an open-array ARRAY OF CHAR parameter assigned to a fixed array) - voc accepts this as an extension, but Oberon2.pdf's own assignment-compatible rule 6 only covers a *string constant*, not a general array value, so this was a real, previously-undetected violation of poc's own strict-bootstrap-source constraint. Fixed with the report's own COPY predeclared procedure. (3) Oberon2.pdf §3's vocabulary rule 4 ("a string of length 1 can be used wherever a character constant is allowed and vice versa") was never implemented at all, silently blocking the ordinary single-quoted-character idiom used throughout Lexer.Mod (ch = ":", CASE ch OF "a": ...). Implemented via a new SemanticActions.IsSingleCharStringLiteral helper (relational operators) plus value-dependent extensions to CheckAssignmentCompatible (assignment/RETURN/value-parameter passing, now also poc's first support for fixed-size ARRAY OF CHAR value parameters taking a string constant, previously missed by CheckArguments) and CheckCaseLabelList (CASE labels). SyntaxTree/Diagnostics/Lexer/Types/MemoryLayout/SymbolTable now all self-check clean under poc -check; ConstantEvaluator/PredeclaredProcedures/ModuleInterface/SemanticActions/Parser/Poc.Mod remain blocked on separate, larger gaps (predeclared-function constant folding, Appendix C/SYSTEM.BYTE, and a diamond-import module-caching bug - see below/PLAN.md's "Open design questions").
