# voc's modules: an inventory

PLAN.md Phase 12 step 3 (2026-09-27): every module Vishap Oberon (voc)
supplies, from its sources, for deciding which poc supports. It is a
record of facts. The decisions: Phase 12 step 4 makes poc compatible with
voc's runtime modules (without `Heap`, but with its finalization); the
modules under `src/library` wait for Phase 18.

## Sources and method

- The source clone `/usr/local/sw/src/lang/Oberon/vishap/compiler`,
  commit `552eade0` (2026-09-18): every `.Mod` under `src/runtime`,
  `src/library/*` and `src/tools/*`, 161 files.
- What voc builds: the targets of `src/tools/make/oberon.mk`. `O2library`
  is `runtime v4 ooc2 ooc ulm pow32 misc s3`; `OClibrary` is `runtime`
  only. `Platform$(PLATFORM)` and `oocC$(DATAMODEL)` pick one variant
  per host.
- What voc installs: `/usr/local/sw/versions/voc/git/{2,C}/sym`
  (136 and 13 symbol files), `lib/libvoc-O2.so`/`libvoc-OC.so`, and of the
  programs only `showdef` (`BrowserCmd`).
- Imports, sizes, voc's inline C (`PROCEDURE -` procedures, whose body
  is C text) and header comments read from each file; licences from each
  file's header, else from voc's `ReadMe.md`, "License".
- "poc -check": each module run through `poc -O2 -emit-interface` in
  import order (`build/bin/poc` of 2026-09-27), with poc-rtl's interfaces in
  place of voc's `Files`, `In`, `Math`, `MathL`, `Modules`, `Out`,
  `Platform`, `Strings` and `Console` - as a program would get them. Only
  a module's *first* error is recorded; more may follow it.
- The tables under "The modules" are generated by
  `tools/voc-inventory/inventory` (its `README.md` says how); the prose
  above them is by hand, to reread when they change. The *Purpose*
  column and what poc's runtime has of each module are kept by hand in
  the scripts.

## Findings

1. **Nearly everything reaches `Platform`.** 99 of the 142 library and
   runtime modules import voc's `Platform` directly or through their
   imports. voc's `Platform` has 46 procedures; poc's had 5 (`Chdir`,
   `GetEnv`, `System`, `Exit`, `Unlink`) until Phase 12 step 5a
   (2026-10-02) gave it all of them. What poc's `Platform`, `Files`
   and `Modules` lacked was the first error of nine modules (`Args`,
   `Reals`, `oocSysClock`, `oocFilesHost`, `MultiArrays`, `Printer`,
   `ethBTrees`, `ethZlibReaders`, `ethReals`), and through them most of
   the rest; since 5a, only the last four, which need `Files`' typed
   riders and `Modules.Halt` (5d, 5e). poc's `Files` has 15 of voc's 37
   procedures (no typed `ReadInt`/`WriteInt`..., `ReadBytes`, `GetDate`,
   search path); `Modules` has the arguments but not the module list,
   commands or `Halt`.
2. **Inline C.** Ten modules contain voc's `PROCEDURE -` procedures,
   C text pasted into the generated C, which poc cannot compile: `Heap`,
   `Modules`, `Out`, `Files`, `Platform` (all replaced by poc's own
   runtime), `oocwrapperlibc`, `ulmSysStat`, and the three `oocX11`
   modules. Anything taken from these is a rewrite with `["C"]` external
   procedures.
3. **zlib is Oberon.** `ethZlib`, `ethZlibInflate`, `ethZlibDeflate` and
   the reader/writer modules are a complete deflate/inflate written in
   Oberon (ETH's); `ethGZReaders`, `ethGZWriters` and `ethZip` need no C
   zlib. (Step 4's criteria in PLAN.md assumed they did.) Only the
   `oocX11` family needs an outside C library (Xlib).
4. **The Oberon system.** Only six modules need `Texts` or `Oberon`:
   `Oberon` itself, `Sets` (v4), and `ethBase64`, `ethDates`, `ethSets`,
   `ethStrings` (s3). voc's `Texts` is a file-based text (no display),
   importing `Files`, `Modules` and `Reals`.
5. **Accepted by poc today** (56 since the four language fixes of
   finding 6 that followed it; 52 once step 5a gave poc the whole of
   `Platform`, 2026-10-02; 34 before that, and 23 before the first
   language fixes of finding 6): `Reals`, `Args`, `oocAscii`, `oocC`,
   `oocCharClass`, `oocComplexMath`, `oocConvTypes`, `oocFilenames`,
   `oocFilesHost`, `oocIntConv`, `oocIntStr`, `oocJulianDay`,
   `oocLComplexMath`, `oocLRealConv`, `oocLRealMath`, `oocLRealStr`,
   `oocLongInts`, `oocLowLReal`, `oocLowReal`, `oocMsg`, `oocOakMath`,
   `oocOakStrings`, `oocProgramArgsHost`, `oocRandomNumbers`,
   `oocRealConv`, `oocRealMath`, `oocRealStr`, `oocRts`, `oocStrings`,
   `oocStrings2`, `oocSysClock`, `oocTime`, `ooc2Ascii`, `ooc2CharClass`,
   `ooc2ConvTypes`, `ooc2IntConv`, `ooc2IntStr`, `ooc2Real0`,
   `ooc2Strings`, `ethMD5`, `ethRandomNumbers`, `ethUnicode`, `ethZlib`,
   `ethZlibBuffers`, `ethZlibInflate`, `ulmASCII`, `ulmDisciplines`,
   `ulmIEEE`, `ulmObjects`, `ulmSys`, `Listen`, `MersenneTwister`,
   `MultiArrayRiders`, `MultiArrays`, `crt`, `powStrings`. (`VT100` was
   one; poc has its own since step 5b.) Accepted means it type-checks,
   not that it runs as under voc.
6. **Language points** (the first error of a module), with what the
   user decided (2026-09-27):
   - `Oberon2.pdf` §3, "A string of length 1 can be used wherever a
     character constant is allowed and vice versa": poc accepted a
     one-character string *literal* compared with a `CHAR`, and a named
     one in an assignment or a `CASE` label, but not a named one in a
     comparison (`ch < Ascii.sp`: `oocCharClass`, `ooc2CharClass`), and a
     character constant never where a string is expected (`COPY(1BX, s)`,
     `s := 1BX`, `s = esc`: `VT100`). voc accepts all of them. A poc
     conformance bug, **fixed**: both ways, for any constant, named,
     imported or literal (fixtures `llvm-char-string-constants`,
     `semantic-reject-char-string`).
   - Text after the module's closing `END M.` (`ethUnicode` ends with
     System 3's binary text trailer): voc ignores it; poc stopped on an
     invalid character. **Fixed**: poc reads nothing after the period.
   - A hexadecimal literal above `MAX(HUGEINT)` (`0FFFFFFFFEFCDAB89H`,
     `ethMD5`): voc takes 16 hex digits as a 64-bit two's-complement
     pattern (that one is -271733879). **Adopted**, with voc's rule, as an
     extension `-strict` rejects (`doc/language-extensions.md`,
     "Hexadecimal constants as 64-bit patterns"; fixture
     `llvm-hex-pattern-literals`).
   - `LONG(ch)` for a `CHAR` (`ethZlibDeflate`): voc gives its ordinal;
     the report defines `LONG` for numbers only. **Not adopted**: poc
     rejects it, and a port writes `ORD(ch)`.
   - `POINTER [1] TO` (`ulmTypes`): voc's untraced pointer, with `SYSTEM`
     imported; poc has no syntax for it (its untraced allocation is
     `SYSTEM.NEW`). `ulmTypes.UntracedAddress` is its only use in the
     library, and nothing uses that (`ulmSysTypes` only re-exports it);
     `SYSTEM.ADDRESS` would serve. **Not adopted**: a port declares it
     `SYSTEM.ADDRESS`, which poc's collector does not trace either.
   - A function procedure with an empty body (`ulmSYSTEM.UNIXFORK`,
     `UNIXSIGNAL`, neither exported nor called): voc accepts it silently;
     poc makes it a compile-time error. `Oberon2.pdf` §10 says "The body
     of a function procedure must contain a return statement", as do the
     1993 report, the 1990 Oberon report, Component Pascal and Active
     Oberon; Oberon-07 makes the `RETURN` part of the syntax. **Kept an
     error**: a port removes the two procedures.
   - Found once step 5a gave poc all of `Platform`, so that more modules
     got further (2026-10-02, decided with the user), all four as voc and
     `Oberon2.pdf` have them (fixtures `llvm-voc-library-fixes`,
     `semantic-voc-library-fixes`):
     - a local declaration hiding an import alias (`oocLComplexMath`: a
       variable `c` and `IMPORT c := oocComplexMath`, then `c.r`): poc read
       `c.r` as the module's `r` ("not an imported module"). **Fixed**: §4,
       a scope "excludes the scopes of equally named objects which are
       declared in nested blocks";
     - writing through a read-only pointer field (`MultiArrayRiders`:
       `s-: SIntPtr`, then `A.s[n] := x`): "assignment target is
       read-only". **Fixed**: `p[e]` is `p^[e]`, and `p^` is "the variable
       which is referenced by p" (§8.1), another variable than `p`;
     - `LEN` of a fixed array as a constant (`oocLRealConv`: `FOR len := 0
       TO LEN(int) - 1` with an `INTEGER` `len`). **Adopted**, typed
       `LONGINT` but assignable wherever its value fits
       (`doc/language-extensions.md`, "Constant expressions");
     - `NIL` as a constant (`oocChannel`: `CONST done* = NIL`). **Adopted**.
       `oocChannel` still stops at its empty abstract function bodies
       (above).
   - Found on the way and fixed (2026-09-27): poc trapped (a failed type
     guard in `Types.FindField`) on a field of a record whose base type
     came from a module that could not be imported; fixture
     `semantic-reject-unresolved-record-base`.
7. **Size model and platform.** Written for particular machines:
   `ulmTypes` (Ulm's compiler on m68k and sparc), `ulmMC68881` (the
   m68k floating-point coprocessor under SunOS 4.1), `ulmIEEE` (i386
   assumptions), `ulmSys` (Linux i386 system call numbers, which
   `ulmSYSTEM.UNIXCALL` only uses as tags to pick a voc `Platform` call),
   `ulmSysTypes`/`ulmSysConversions` (C structure layouts), `oocC` (a C
   data model per variant), `Reals`, `ethReals`, `oocLowReal`,
   `oocLowLReal` (IEEE layouts through `SYSTEM`), `Printer` (V4's
   PostScript printing). None of the library has been compiled by voc
   under `-OC`.
8. **Overlap.** Strings: `Strings`, `oocStrings`, `oocStrings2`,
   `oocOakStrings`, `ooc2Strings`, `ethStrings`, `powStrings`,
   `ulmStrings`. Random numbers: `MersenneTwister`, `oocRandomNumbers`,
   `ethRandomNumbers`, `ulmRandomGenerators`. Real/string conversion:
   `Reals`, `ethReals`, `oocRealConv`/`oocRealStr`/`oocLRealConv`/
   `oocLRealStr`, `ooc2Real0`/`ooc2LRealConv`, `ulmReals`. Sets: `Sets`,
   `ethSets`, `ulmSets`. Character classes and ASCII names: `oocAscii`,
   `ooc2Ascii`, `ulmASCII`, `oocCharClass`, `ooc2CharClass`. Declared
   obsolete by their own headers: `oocFilenames`, `oocStrings2`, and
   `oocSysClock` ("PRIVAT. Don't use this").
9. **Licences.** poc is BSD 3-Clause. From the files' headers: the OOC
   modules (ooc, ooc2, and voc's `Math`/`MathL`, adapted from them) are
   LGPL 2.1 or later; the Ulm library is LGPL 2 or later (voc's
   `ReadMe.md` says GPL); `MersenneTwister` and `MultiArrays`/
   `MultiArrayRiders` are LGPL 2 or later; the s3 modules refer to the
   "General ETH Oberon System Source License", whose text is not in the
   tree (to be fetched and read before step 4 relies on it);
   `powStrings` has a copyright and no licence; `Listen` names a web page
   and an author and no licence. Files with no header fall under voc's
   `ReadMe.md`: the runtime "GPLv3 with runtime exception" (most of it),
   Ofront's parts FreeBSD, the tools GPLv3. poc's `rtl/llvm` is its own
   code, not derived from voc's (its `Math`/`MathL` are written over
   libm, not from the LGPL modules).
10. **Oakwood.** voc's runtime has the Oakwood basic modules `In`, `Out`,
    `Files`, `Math`, `MathL`, `Strings`, which poc has too (`Files`
    partly); `oocXYplane` is Oakwood's `XYplane` (X11). voc has no
    `Input`.
